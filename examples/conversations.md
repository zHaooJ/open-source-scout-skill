# 对话与交付示例

[返回首页](../README.md) · [查看工作流程](../docs/workflow.md)

以下均为**教学示例**，展示提问和交付方式，不代表已经进行实时搜索、核验或运行测试。示例中的方案 A/B 为虚构类别，不是具体项目推荐。实际结果必须使用查到的项目及来源。

## 示例一：只有模糊需求

**用户**

```text
使用 $open-source-scout 帮我找一个开源知识库，我还没想好用哪个。
```

**助手**

> 主要给谁使用？（单选，也可以直接描述）
>
> A. 自己整理笔记和资料  
> B. 团队共享文档和经验  
> C. 面向客户提供帮助文档  
> D. 不确定，先看几种方案

**用户**

```text
B。我们已经有很多文档，主要是找起来麻烦。
```

**助手**

> 更希望怎样找到资料？
>
> A. 输入关键词，快速找到原文  
> B. 用自然语言提问，得到带出处的答案  
> C. 两者都需要，暂不确定优先级  
> D. 先解释接入和维护上的差别

如果用户选 D，下一步应解释路线，并按需要核查代表方案。没有证据前，不预设问答系统一定更贵、全文搜索一定更简单。

**演示的原则：** 先由场景找到搜索方向，不默认“知识库”就是带大模型的产品。

## 示例二：需求已经足够清楚

**用户**

```text
使用 $open-source-scout 找几个可接入自有 Agent 的长期记忆模块。
重点记录项目进展、决策和待办。明确任务状态优先，自动补充背景。
语言和部署方式暂不限，请介绍项目并比较接入成本。
```

**合适的下一步**

简述采用的条件，进入搜索，不再问“你要记住什么”“用什么语言”。围绕以下事实核查候选：

- 是否有可接入现有 Agent 的接口。
- 是否能区分当前状态与历史信息，决策变化如何处理。
- 是否保留来源和时间，如何组织不同项目的数据。
- 开源版有哪些能力，需要部署哪些组件或调用哪些外部服务。

如果记忆模块只负责背景检索，应说明还需任务状态存储，不能把它描述成完整任务管理系统。

**演示的原则：** 信息充分就执行；项目的事实缺口由检索解决。

## 示例三：用户想先看方向

**用户**

```text
使用 $open-source-scout 帮我找开源 Agent 项目。
先少问一点，给我看几种方向，我现在也不知道要什么。
```

**合适的交付形式**

先探索有区分度的路线，例如完整助手、可集成框架、适合阅读的参考实现。每条给出经过实际核查的代表项目、主要用途和用户要承担的工作，再问哪条更接近目标。

不要求先确定语言、数据库、预算、云平台等全部字段，也不把尚未核查的熟悉项目当成最终推荐。

**演示的原则：** 用真实差异帮助形成需求，同时保留探索结果的暂定性质。

## 示例四：用户已有候选和硬条件

**用户**

```text
使用 $open-source-scout 比较我发来的三个仓库。
我要在内网运行，处理数据时不能调用外部服务，重点看开源版功能。
```

**合适的下一步**

优先检查指定仓库的部署文档、数据路径、模型调用和许可证。首次安装是否需要下载资源，与运行时是否联网分开核验。

如果某项目确实要求外部服务，应标为不满足此条件。可以继续核查其余候选，不必先要求用户放宽内网要求。

**演示的原则：** 指定范围和硬条件会改变检索策略，不能让高热度抵消不符合的条件。

## 示例五：输出应该让人认识项目

下面是假设“团队资料检索”场景的**结构示意**。真实交付需替换为已核查项目，并在事实附近附具体来源。

| 候选角色（虚构示例） | 简单介绍 | 在当前任务中怎样使用 | 需要承担的工作与限制 |
| --- | --- | --- | --- |
| 方案 A：完整资料管理产品 | 集中管理团队文档，提供成员使用的检索入口 | 团队通过现有界面上传和查找资料 | 需要核对数据迁移、权限和检索能力是否满足要求 |
| 方案 B：可嵌入的检索组件 | 提供资料索引与查询接口，供开发者接入自己的系统 | 把检索能力接到已有业务平台 | 需要自行完成界面、权限以及与业务的集成 |

表后的总结应解释选择，例如：

> 如果当前最重要的是让团队尽快开始使用，优先验证完整产品路线；如果已有系统必须保留，重点比较组件的接口与接入工作量。最终建议取决于查到的功能和实际限制，不能仅按项目类型决定。

这类总结说明“为什么选”，而不只是把表格重述一遍。

## 示例六：用户看不懂或修改需求

**用户反馈**

```text
这些项目分别是做什么的？我看不懂 SDK 和框架的区别。
```

**合适的调整**

复用已核查的材料，用一个共同任务解释每个项目承担的部分；说明哪些能力已经提供、哪些需要自己开发。除非用途也发生变化，不重新发需求问卷。

如果用户改为“我只想找装好就能用的”，才更新使用方式并重筛受影响候选。

## 可以直接复制的请求

```text
使用 $open-source-scout 找一个某类商业产品的开源替代品。
先问我最在意哪些能力，再比较真实替代范围和限制。
```

```text
使用 $open-source-scout 找适合学习 Agent 工具调用机制的开源项目。
我主要看源码和例子，请说明从哪里开始读。
```

```text
使用 $open-source-scout 分析这些仓库链接。
只依据我提供的材料比较，查不到的部分明确标为未知。
```
