# 比较、交付与反馈

用于从候选形成建议，或根据用户反馈修正结果。输出只保留当前阶段需要的信息，不要求每次生成完整报告。

## 比较顺序

1. 按用户硬条件检查适用性。已证实违反硬条件的候选不能放入“完全符合”的推荐；关键项待确认的候选保持有条件。
2. 区分候选角色：可直接采用、需要集成的组件、学习参考、相关但不适用。需要组合才能实现目标时，明确组合成本，不能把一个组件描述为完整产品。
3. 根据用户用途比较偏好及实际投入；偏好未知而取舍会改变推荐时，基于已核实差异提出选择题。
4. 分别表达需求匹配、项目质量与证据把握程度。热度高不证明适合，小众不证明质量差，未检查不代表低质量。

| 使用目的 | 更应检查的方面 |
| --- | --- |
| 直接部署 | 实际功能、部署依赖、操作难度、迁移、稳定性与维护成本 |
| 集成或二次开发 | 接口、架构与扩展点、兼容性、需要改动的模块、许可及长期维护成本 |
| 学习源码 | 代码规模与可读性、文档和示例、实现完整度、适合的学习路径 |
| 参与贡献 | 贡献指南、可参与的问题、维护者响应及项目协作方式 |

默认用可解释的定性比较。只有用户要求或评分确实帮助决策时才评分，说明维度、依据与权重；未知项和不适用项单独标记，不能机械记零分，也不能让高总分抵消硬条件失败。不输出无依据的采用成功率。

## 项目介绍与可理解的比较

默认让用户不打开仓库也能认识每个主要候选。区分两层信息：

- **项目简介**：它是什么类型的项目、主要解决什么问题、通常怎样使用。用简短自然语言说明，不以功能名词堆叠代替介绍。
- **需求匹配**：它在用户当前任务中承担什么，已有能力能帮到哪里，用户还需集成、开发或配置什么。

按对话中体现的熟悉程度调整解释。用户熟悉领域或明确只要链接、参数时可以压缩；缺少背景时解释影响选择的术语，不为此新增必答问卷。例如，“可嵌入 SDK”可以解释成“把这项能力接入自己的程序，再设计界面和业务流程”。

比较采用与用途相关的共同维度。例如，二次开发可比较已提供的能力、可修改的接口和需要自行完成的工作；直接部署可比较实际使用流程、依赖和运行投入。对候选回答相同的问题，避免一个只讲功能、另一个只讲语言、第三个只讲热度。项目类型不同时，说明它们在同一目标中承担的不同部分，不强行当作可互换方案。

抽象能力不容易理解时，用用户的一个典型任务贯穿说明：各项目怎样参与完成任务、哪部分已有支持、哪部分需要补齐。场景和项目简介同样需要证据；推演用法应明确是示例或建议，不能写成已经集成或实测成功。没有帮助时省略场景，不强制逐项扩写。使用“轻量”“开箱即用”“更容易”等判断时，说明具体指向及依据；依赖规模、默认功能和用户开发投入不能混为一谈。

## 针对首选的反向核查

在形成明确采用建议前，围绕最关键的推荐理由检查可能使项目不适用的事实：

- 因“功能满足”推荐：功能是否实际发布，是否只在付费版、托管版或规划中？
- 因“离线或私有部署”推荐：相关数据路径是否仍调用外部 API 或身份服务？
- 因“易用或便宜”推荐：是否有用户缺少的硬件、运行服务和持续维护投入？
- 因“可扩展”推荐：是否找到实际接口或需要改动的模块，兼容范围是否明确？
- 因“适合学习”推荐：是否能定位清晰示例与核心路径，而非只根据项目介绍判断？

按任务挑选需要的检查，不执行无关的全面审计。不默认安装或试跑；如果运行验证已经得到用户授权，则记录实际环境、版本和观察，且只声称验证过的范围。导入成功、示例运行与真实目标场景验证是不同结果。

## 输出菜单

用户指定格式优先。默认在聊天内输出，随复杂度选用以下内容。

**探索方向**：给少量有区分度的路线，每条说明解决什么、适合谁、主要投入、已核查的代表项目与重要未知。下一轮给与真实差异相关的选择题；如果只是概念路线、还未查真实项目，要直接说明。

**定向搜索**：用简短需求摘要、项目简介和候选对比，注明重要匹配、限制与证据。列表长短由候选质量和用户要求决定。

多个候选默认可用下面的表格；列按任务调整，单个候选或用户指定其他格式时不必制表。面向不熟悉项目的用户，保留能解释“它是什么、做什么”的简介：

| 项目与链接 | 简单介绍：是什么、主要做什么 | 如何用于当前需求 | 主要差异、投入与限制 |
| --- | --- | --- | --- |

将共同维度落实到各行，来源链接放在其支持的事实附近。许可、语言、版本、环境等按决策重要性增加列或放在紧邻的说明中；影响入选的硬条件和关键未知要显著保留，不以排版简洁为由隐藏。

候选对比后给与当前阶段相符的选择总结：探索时概括路线差异；需求足够明确时说明优先考虑谁及原因、什么条件下应改选、哪个关键未知可能改变判断。总结解释选择，不只重复表格或给出排名。只总结有依据的差异，不为了填满结构虚构改选条件或待验证项。

**深入比较**：可以先给推荐或条件式结论，再展开项目定位与关键取舍。结合上面的选择总结，给出能验证决定性差异的最小动作。用户还在认识候选时，避免用确定排名代替解释。版本、许可与时效信息仅在相关时列出，关键未知不要藏在表尾。

**没有完全符合的项目**：说明本次范围中缺了哪项能力或受什么限制；分别列出确实不满足与尚未核实的情况。可给“保持原条件换路线／接受某项明确取舍／先核实一个关键未知”的选择，不能默认用户同意放宽要求，也不能声称整个生态不存在方案。

来源尽量链接到支持结论的具体文档、许可证、代码或发行说明；项目主页用于身份与入口。只需说明会影响结论的覆盖限制，不重复堆叠泛泛免责声明。

## 反馈与后续

用户说“太复杂”“想要中文支持”“更想学习”时，将其转换成新的或修正的需求，必要时用一题区分含义。例如“中文支持”可能指中文界面、中文文档或中文内容处理，不要擅自选择其中一种。

用户说“看不懂这些项目是做什么的”时，先补充项目简介、术语解释或共同场景，复用已有可靠证据；只有反馈实际改变了用途或取舍才重筛候选，不重复启动需求问卷。

重新检查受影响的硬条件、候选角色和排序；未变化的来源继续复用。用户选择候选后，收敛到其关键缺口和下一步，除非有新证据或用户要求，不重新开启全量选型。

交付后的下一步可以是阅读一个入门示例、核查一个部署条件、在用户授权范围内做一个小型验证。不要把“可以验证”写成“已验证”，不要自动创建长期监控或安装未知代码。

需要交给后续开发或验证工作时，保留一个紧凑说明：所选仓库与版本、用户目标和硬条件、决定性证据位置、尚未核实事项、建议验证动作及用户已有授权范围。无需复制所有搜索记录和完整 README。

## 交付前检查

- 是否回答用户当前需要的探索、清单或比较，而不是强行交付另一阶段的结果？
- 在当前所需解释深度下，用户不打开链接能否知道主要候选做什么、属于哪种项目、自己还需完成什么？
- 候选是否围绕共同问题比较，实际差异与选择总结是否能帮助用户判断？
- 是否把已回答问题重复询问，或将模型假设误记成用户条件？
- 是否有硬条件失败或关键未知被包装成完全符合？
- 是否混用了版本、edition 或完整产品与组件的角色？
- 关键推荐理由是否能追溯到已检查来源，声明、推断和运行结果是否区分？
- 是否完成与首选理由相关的反向核查，并据发现修正结论？
- 下一步是否具体且与用户实际授权一致？

发现问题后修正受影响的结论；没有新变化或疑点时不重复整套检查。
